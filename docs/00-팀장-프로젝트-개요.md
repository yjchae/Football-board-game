# 👔 개발 팀장 — 프로젝트 개요 & 의사결정 기록

## 1. 목표
실물 축구 카드를 사진으로 찍어 나만의 팀을 만들고, AI(제미나이/클로드)가 경기를 중계·시뮬레이션해 주는 **아이들용 웹 보드게임**.
설치 없이 링크로 접속해서 바로 즐길 수 있어야 한다.

## 3. 핵심 기술 결정 (ADR 요약)

### ADR-1. 웹 프레임워크: React + TypeScript + Vite (Flutter 대신)
- **결정**: React 19 + TypeScript + Vite 정적 사이트
- **이유**
  1. 요구사항 7번 "사이트에 바로 접속" → 정적 웹이 가장 단순 (GitHub Pages 무료 배포)
  2. 드래그앤드롭을 **터치(태블릿)** 에서도 안정적으로 → `@dnd-kit` 사용
  3. 브라우저 자동화(Playwright)로 실제 화면 QA 가능 — Flutter Web(캔버스 렌더링)은 자동 QA가 어려움
  4. 현재 개발 환경에 Flutter SDK가 설치되어 있지 않아 빌드 검증이 불가했음
- **트레이드오프**: 선호하시는 Flutter가 아님. 추후 모바일 앱이 필요하면 `src/domain`(순수 TS 로직)을 Dart로 옮기기 쉬운 구조로 분리해 두었다.

### ADR-2. 서버 없음 (BYOK: 본인 키 연결)
- **결정**: 백엔드 서버 없이 브라우저에서 AI API를 직접 호출. 사용자가 **본인 키**를 설정 화면에 입력, 그 기기 브라우저 저장소(IndexedDB)에만 저장.
- **이유**: "제미나이 계정은 본인 계정을 연결" 요구사항 + 서버 운영비 0원 + 키가 남의 서버를 거치지 않음
- **주의**: 제미나이 "계정 로그인(OAuth)"으로 API를 직접 쓰는 방식은 일반 개인 계정용으로 제공되지 않는 것으로 알고 있어, Google AI Studio에서 **본인 계정으로 발급한 API 키**를 연결하는 방식으로 구현했다. [보통 확신 – 검증 권장]

### ADR-3. AI는 "해설·이벤트 생성", 점수 계산은 게임 엔진
- AI가 말한 점수/선수를 그대로 믿지 않는다. 응답을 **검증기(`src/ai/parse.ts`)** 가 거르고, 점수·통계는 이벤트로부터 직접 계산한다.
- AI 호출이 실패하면 그 구간만 **오프라인 엔진**으로 자동 대체 → 아이가 보는 경기는 절대 멈추지 않는다.

### ADR-4. 한 하프 = 15분 × 3구간
- 매 구간마다 AI를 호출 → 구간 사이에 "작전 타임(교체)"을 넣을 수 있어 요구사항 8번(중간 교체)을 만족.
- 마지막 구간 응답에 하프 정리(요약/MVP)를 함께 받는다 → 하프당 AI 호출 3회.

### ADR-5. 홈 화면 앱(PWA)으로 기기별 사용
- **결정**: 웹 앱 매니페스트 + 서비스 워커를 추가해 "홈 화면에 추가"로 설치. 키·팀은 설치한 기기에만 저장.
- **이유**: 보호자가 집 태블릿 한 대에 키를 넣어두고 아이가 그 기기에서만 쓰는 사용 방식. 앱스토어 등록 없이 설치 가능.
- **주의**: iOS는 사파리와 홈 화면 앱의 저장소가 분리되어 있어, 설치 후 앱 안에서 키를 입력해야 한다. [보통 확신 – 실기기 검증 권장]

### ADR-6. 고정 칸 → 좌표 기반 자유 위치
- **결정**: 라인업에 자리별 좌표(`positions`)를 저장하고, 역할은 좌표로 계산. 포메이션은 출발점일 뿐.
- **이유**: 원하는 위치에 자유롭게 놓고 싶다는 요구 + 사진 속 카드 위치를 그대로 옮기려면 좌표가 필요.
- **호환**: 좌표가 없는 기존 저장 데이터는 포메이션 기본 위치로 그대로 동작.

### ADR-7. 저장소: localStorage → IndexedDB
- **결정**: 카드 사진 때문에 localStorage(약 5MB) 한도에서 데이터가 조용히 유실되는 결함(QA Q2) → IndexedDB로 이전.
- **호환**: 첫 실행 시 예전 localStorage 데이터 자동 이전. IndexedDB를 못 쓰는 브라우저는 localStorage로 대체하고, 저장 실패 시 화면에 경고.
